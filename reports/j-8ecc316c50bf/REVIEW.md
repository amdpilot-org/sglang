## Finding

Transformers 4.57+ normalizes the old per-layer `compress_ratios` list into two fields:

- `layer_types`: one attention type string per layer
- `compress_rates`: a dictionary mapping attention type to rate

The required compatibility conversion is equivalent to:

```python
[config.compress_rates.get(layer_type, 0) for layer_type in config.layer_types]
```

The candidate instead treats `compress_rates` as a renamed list, copies it directly to `compress_ratios`, and counts values by iterating it. Its tests likewise use the non-contract fixture `"compress_rates": [0, 4, 128, 0]`.

With a real config generated by the pinned Transformers 5.12.1 `DeepseekV4Config`, the recorded base reproduces the reported `AttributeError` during `ModelConfig` construction. The expected ratios for the four-layer adversarial fixture are `[128, 4, 128, 4]`.

At the exact candidate commit, the same generated config does not reach `ModelConfig`: `_try_load_deepseek_v4_config` forces the raw V4 dictionary through SGLang's V3-derived alias, which fails validation on V4's generated `mlp_layer_types` (`hash_moe`). This is an earlier failure than the original one. Independently, if this validation were bypassed, the candidate would expose the `compress_rates` dictionary as `compress_ratios`; integer layer indexing in `DeepseekV4Attention` would fail and `get_num_indexer_layers` would incorrectly return zero.

The candidate also aliases the complete nested modern `rope_parameters` object directly to `rope_scaling`. The generated structure has `main` and `compress` sub-configurations, so it is not equivalent to the flat Yarn dictionary used by the candidate tests. This path was not qualified for model accuracy.

This is fixed on current `main` (`6cee9285a`). The fix landed in #34166, which was not linked to this issue — which is probably why this and #30886 are both still open.

Verified on Apple Silicon:

```
$ python -m pytest test/registered/unit/hardware_backend/mlx/test_metal_profiler.py -q
10 passed, 17 warnings in 7.22s

$ python test/run_suite.py --hw mlx --suite stage-a-unit-test-mlx
Test Summary: 21/21 passed
```

with `MTL_CAPTURE_ENABLED` and `SGLANG_USE_MLX` both unset, i.e. the configuration that used to fail.

## Where the fix came from

@jlee5814's and @now-ing's diagnosis above was correct: the manager takes the MPS strategy (`torch.mps.profiler.metal_capture`), but both tests patched `mx.metal.start_capture`, the *MLX* strategy's entry point, so a real Metal capture ran and failed without `MTL_CAPTURE_ENABLED=1`.

`2969ab3d4` ("[MLX] Window-bounded SWA KV storage and in-graph sampling", #34166, merged Aug 10) changed exactly that:

```
$ git log --oneline -S "torch.mps.profiler" -- test/registered/unit/hardware_backend/mlx/test_metal_profiler.py
2969ab3d4 [MLX] Window-bounded SWA KV storage and in-graph sampling (#34166)
0a28a929d [MLX] Add Metal profiling hooks to server profiler (#28122)
```

Its diff swaps `mx.metal.start_capture` → `torch.mps.profiler.metal_capture` in both tests, adds a `MagicMock` capture context with `__enter__`/`__exit__` assertions, and asserts the injected message in the failure test. #34166's description states the same root cause in the same terms, so this looks like an independent rediscovery rather than an adoption of #30886.

`5af518335` (#34300, Aug 10) then hardened the class against an ambient `SGLANG_USE_MLX=1` by pinning `profiler.use_mlx` to `False` in `setUp` — a second, separate hazard on the same tests.

I think it's just a difference between  long-time metric and short-time peak metric. From the perspective of bench_serving, estimating token throughput using TPOT (Time Per Output Token) provides a comprehensive evaluation over the entire testing period. On the other hand, the throughput printed in the engine log refers to the number of tokens generated within a single logging interval (which can be understood as the time for 40 consecutive decodes) divided by the time taken. Clearly, the data in the engine log is influenced by various factors, including: the potential interleaving of the prefill phase between decodes, which extends the total time; additionally, the amount of remaining memory also affects the number of tokens output per decode. Of course, the core issue here is that the engine log records short-term peak throughput, and similar results might be obtained if using the P25 (25th percentile) of TPOT for estimation.

I think I've found the cause. In multiple tests, when the backend is specified as "sglang," the `flush_cache` function is called to clear the cache.

 If `flush_cache` is executed successfully, there will be an inconsistency in the Decode Throughput between `bench_serving` and `engine logs`, specifically, `bench_serving` will be lower than `engine logs`. 

If `flush_cache` fails, the difference in Throughput between the two is within an acceptable range.

I speculate that the time loss caused by the successful execution of `flush_cache` might be the reason. The Decode Throughput in `engine logs` is not affected by this, but `bench_serving` is. I'm still not sure how to fix it. Does anyone have any suggestions?

When the backend is specified as "sglang," the following code is called to flush the cache，code in [here](https://github.com/sgl-project/sglang/blob/9cf407729441a18561ee5a8b2c1e3e535ba817f9/python/sglang/bench_serving.py#L961):
```python
# Flush cache
if "sglang" in backend:
    requests.post(base_url + "/flush_cache")
```

The specific implementation of `flush_cache` can be found [here](https://github.com/sgl-project/sglang/blob/9cf407729441a18561ee5a8b2c1e3e535ba817f9/python/sglang/srt/managers/scheduler.py#L1677):
```python
def flush_cache(self):
    """Flush the memory pool and cache."""
    if len(self.waiting_queue) == 0 and (
        self.running_batch is None or len(self.running_batch.reqs) == 0
    ):
        self.tree_cache.reset()
        self.tree_cache_metrics = {"total": 0, "hit": 0}
        if self.grammar_backend:
            self.grammar_backend.reset()
        self.req_to_token_pool.clear()
        self.token_to_kv_pool.clear()

        if not self.spec_algorithm.is_none():
            self.draft_worker.model_runner.req_to_token_pool.clear()
            self.draft_worker.model_runner.token_to_kv_pool.clear()

        self.num_generated_tokens = 0
        self.forward_ct_decode = 0
        self.spec_num_total_accepted_tokens = 0
        self.spec_num_total_forward_ct = 0
        torch.cuda.empty_cache()
        logger.info("Cache flushed successfully!")
        if_success = True
    else:
        logging.warning(
            f"Cache not flushed because there are pending requests. "
            f"#queue-req: {len(self.waiting_queue)}, "
            f"#running-req: {0 if self.running_batch is None else len(self.running_batch.reqs)}"
        )
        if_success = False
    return if_success
```

I went through both sides of this with the current code (main @ 99b9109). Happy to turn any of it into a fix if wanted, but evidence first.

**The two numbers are different estimators, not two measurements of the same thing:**

| | bench_serving | engine log |
|---|---|---|
| definition | TPOT-derived, per request: `(latency − ttft)` over `output_len − 1`, averaged across the whole run, client-side | `num_generated_tokens / gap_latency` where `gap_latency` is the time since the previous log line (`scheduler_components/metrics_reporter.py:799,894`) |
| window | entire run: queueing, any cold start, `[DONE]` tail included | one reporting interval, near-instantaneous |

So bench < engine is expected whenever the run has any ramp-up: the engine line reads close to a short-window peak, the bench number is a whole-run average.

Three smaller things verified along the way (all `python/sglang/benchmark/serving.py` unless noted):

1. TPOT arithmetic is the standard upstream vLLM formula (`(latency − ttft)/(output_len − 1)`, `:1136`): sound.
2. `itl` is recorded per stream **event**, not per token (`:334-337`, `:466+`). Events carrying several tokens (stream-interval batching, speculative decoding) contribute one itl sample, so `len(itl) < output_len − 1` and ITL percentiles conflate event latency with token latency. A retokenized correction already exists, but only for the `sglang-oai` backends (`:1131-1135`, `:1145-1155`); the completions/chat paths don't get it. I wrote CPU unit tests pinning this behavior (sum(itl) + [DONE]-tail == latency − ttft exactly; mean(ITL) > TPOT for the same request from denominators alone). Happy to PR them.
3. `should_flush_cache` is `("sglang" in backend AND SGLANG_IS_IN_CI) or --flush-cache` (`:1467-1471`), not default-on, so the cold-start mechanism discussed earlier in this thread needs CI or the explicit flag to apply to a default run.

If it's useful, the options I see: (a) a note in the bench output clarifying the window difference vs engine logs, (b) an engine-side long-window average for apples-to-apples runs, (c) extending the retokenized ITL path to the other backends. Which, if any, would you want?
